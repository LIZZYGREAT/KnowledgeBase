# Architecture and implementation scope

## Current phase

The current product is a single-user learning and research assistant, prioritizing Terms and paper discovery/review/collection. Obsidian is the main note-reading and writing tool. The current implementation phase is **Learning Progress Context + Progressive Recommendations**: user-selected formal learning notes provide scoped progress evidence for Terms and Research; users can edit local layered context; updates are incremental; existing Publisher, Term review, Research Runtime and explicit scheduling boundaries remain in force. It does not add multi-user support, a new notes platform, or rebuild Collections. See [Product principles](PRODUCT_PRINCIPLES.md).

**Phases 0–14 are implemented; Phases 1–5 and 13 are complete and frozen, and Phase 14 implementation is complete. Performance Phases A–B are complete and frozen; production acceptance remains pending.** The personal-use revision is implemented and verified locally; this does not assert a new CI or production acceptance result. GitHub Actions is the authoritative source for current CI status. Runtime SQLite schema version is 19. Phase 13 includes the Collection Explorer + Unified Workspace convergence and final Runtime Draft, Publisher, Import, navigation, batch-preflight, discard, and restore correctness fixes. Phase 14 explicitly extends GitManager's canonical tracked roots from `knowledge/` to `knowledge/` and `config/research/profiles/`; never allowlist the entire repository. Performance Phase C is deferred pending production profiling. Live Provider/DeepSeek smoke checks, systemd execution, and production backup/restore require operator-provided host access and data.

**The implemented product includes PDF Corpus, Knowledge State, Term Discovery, Research readiness integration, bounded external discovery, and the Home, Terms, Library, Review, Collection Explorer, and Unified Workspace flows.** The Term Core contract remains: Terms support `concept`, `entity`, and `vocabulary`; Runtime Candidates, Evidence, accepted entity relations, rejection memory, and merge audit use SQLite schema 19. A human-reviewed Existing acceptance creates explicit Runtime relations. Term Merge updates the survivor and removes losers in one Publisher Git commit, preserves old IDs as aliases, migrates Runtime references transactionally, and never rewrites Documents.

The current formal rules are:

- Proposals have one lifecycle: `proposed` → `drafted` → `merged` or `stale`, with `rejected` as the explicit rejection outcome. There are no approve or merge endpoints. Applying a Proposal updates its linked Draft; only `Publisher` publishes Drafts, and Proposal finalization is post-publish processing.
- `useRuntimeDraftSession` centralizes frontend Runtime Draft revision, compare, rebase, reload, discard, and conflict behavior used by Workspace and Collection Drafts. Unmount cleanup never starts a save; internal navigation flushes dirty Drafts first and stays on the current page if saving fails. `beforeunload` warns only while a Draft is dirty.
- Browser Back and Forward run the same navigation guards as internal navigation. Ordinary Draft discard is disabled while saving or resolving Runtime or Canonical conflicts; the Runtime session also rejects discard during a save or Runtime conflict.
- `CanonicalTargetResolver` is the single owner of canonical entity target paths and metadata resolution for Draft API workflows, publishing, and ImportService. It validates metadata, IDs, indexed paths, and repository containment without scanning the knowledge tree for duplicate IDs.
- `Publisher.publish(draft_id, expected_revision, ...)` requires the revision the user reviewed. `publish_batch` and batch preflight accept `(draft_id, expected_revision)` pairs and reject duplicate Draft IDs and invalid revisions. Batch preflight validates the prospective Document and Collection state without writing canonical files.
- Canonical Document, Term, Source, and Collection IDs are unique within each entity type. Repository checks, full index rebuilds, and Publish validation fail when an ID appears in more than one canonical file.
- Term metadata types are `concept`, `entity`, and `vocabulary`. Candidate Evidence and accepted entity relations are persistent Runtime state; explicit wiki links remain rebuildable Backlinks and are not duplicated as Runtime relations.
- Term Merge is a Publisher-owned canonical operation. It commits the updated survivor and loser deletions together, preserves loser identifiers as aliases for old links, and migrates Runtime relations and Candidate Term references within one SQLite transaction. Losing bodies are never appended to the survivor.
- Frontend checks use TypeScript and Vitest; there is no JavaScript implementation paired with declaration files or Node's test runner.
- Legacy Import compatibility is isolated in its adapter; standard Import processing has no legacy branch.
- Runtime API routes are split by domain and aggregated by `backend/app/api/runtime.py`.
- Explorer feature hooks own their workflow state; the controller composes those features. Styles are split into domain stylesheets imported by `frontend/src/styles/index.css`.

## Data boundaries

- `knowledge/` contains canonical Markdown and YAML.
- `knowledge/collections/` contains canonical Collection YAML. Collections organize references to Documents, Terms, and Sources without changing their canonical paths or adding reverse membership metadata to entity frontmatter.
- `runtime/` contains persistent, noncanonical application state. Runtime data is not a source of canonical knowledge, but user decisions and operational history must be retained in database backups.
- Collection membership, search, relationship, and other canonical-knowledge indexes are derived from canonical Markdown/YAML and are rebuildable. Reading progress and usage-event history are persistent Runtime SQLite state and are included in database backups, not Git.
- `presentation_annotations` live in Runtime SQLite. Highlight, text color, and underline never modify Markdown/YAML, Git, Search, Context Export, Evidence, or PaperSkillWork. These personal annotations are persistent Runtime data and require the database backup for recovery.
- `storage/` contains local papers, uploads, and staging files and is not committed.
- Parser and linter code is deterministic and does not access external services or persistent state.
- `Publisher` is the only business service that writes canonical files. A Draft stores its comparison Git revision and target content hash; human rebase and successful Publish advance that comparison point. Publish conflicts depend on the target file's content hash, including whether the target is absent.
- Drafts store the canonical target hash for Publish conflict checks. Proposals store the Draft working-content hash they were generated from; unrelated Git commits do not stale either one.
- `GitManager` restricts file operations to Markdown and YAML under `knowledge/` and the explicit `config/research/profiles/` root; never allowlist the full repository. `Publisher.restore` validates historical content and the complete prospective repository reference state before committing; a failed validation or commit restores the previous file bytes. Restore never rewrites Git history.
- Unresolved wiki links may remain in published Markdown. Ambiguous links, invalid citations, and dangling taxonomy or Source references block publishing.
- Publish validates the target and the registries it depends on. Removing taxonomy IDs checks for references to those IDs. `python tools/kb.py check` performs repository-wide reference and duplicate-ID validation; a full index rebuild rejects duplicate canonical entity IDs.
- Current Markdown must pass the writing standard. Legacy Markdown may publish with writing-style warnings; broken frontmatter and other structural errors still block it.
- Proposal content is applied to its linked Draft by `ProposalService`. `Publisher` accepts Draft IDs only, writes canonical files, and finalizes matching applied Proposals after the canonical commit succeeds; a mismatched applied Proposal becomes stale.
- SQLite search and relationship indexes are derived from `knowledge/`; Drafts are not indexed. `python tools/kb.py rebuild` recreates indexes without changing canonical files or usage-event history.
- Runtime SQLite is persistent application state, not a rebuildable index. Drafts, Proposals, Import Jobs and Items, usage-event history, reading progress, presentation annotations, Research Works, Discoveries, Analyses, Candidate decisions and notes, watermarks, Runs, manual requests, pauses, and control events cannot be reconstructed completely from canonical files. Versioned `user_version` migrations preserve these records; do not delete the local database to apply an upgrade.
- Production backups include a consistent SQLite snapshot so persistent Runtime state can be restored with the canonical Git bundle and `storage/` files. Derived indexes can be rebuilt from canonical files and retained usage-event history.
- Publish and Restore return success after the canonical Git commit. Proposal status or index refresh failures are returned as warnings; `python tools/kb.py rebuild` repairs derived indexes.
- Import Jobs and Items live in Runtime SQLite. `storage/staging/` holds temporary import copies, and `storage/papers/` holds local PDFs; neither directory is committed. Import uses no AI or network service.
- Learning context, selected source IDs, preferences, layered Markdown memories and sync checkpoints live under ignored `storage/learning-context/`; do not add them to canonical knowledge or Git. The context service validates every source against canonical Document metadata and has no network dependency for reads. AI updates are structured results that the service validates and merges only into auto-managed entries; pinned user content is preserved. Research and Term recommendation services share this context without changing the meaning of formal review elsewhere.

## Technology

The stack is React + TypeScript + Vite, Python + FastAPI, SQLite + FTS5, Markdown + YAML, Git, DeepSeek API, and Docker Compose. Production serves the static Reference Hub through Nginx and keeps the API off the host-published ports. Registries and resolvers remain file-backed. Drafts, Proposals, Imports, usage history, reading progress, Research decisions and provenance, and presentation annotations are persistent Runtime state; only the Publisher writes Canonical Markdown and YAML. The backend uses `KNOWLEDGE_REPO_PATH` as its repository root and `DATABASE_PATH` for Runtime SQLite.

## Phase 4: Publisher + Git

`Publisher.publish(draft_id, expected_revision, commit_message=None)` requires the reviewed Draft revision before writing its canonical target. Batch Publish accepts a sequence of `(draft_id, expected_revision)` pairs. Document and Term Markdown use their metadata schemas and writing standard; Legacy writing-style findings are warnings, while structural errors remain blocking. Source and Taxonomy YAML use their canonical schemas. The canonical target's content hash determines Draft conflicts; Proposals are applied to Drafts only after checking their base content and the expected Draft revision. Unrelated commits do not block publishing. Document and Term references are checked against their registries, and ambiguous wiki links are rejected without choosing a candidate automatically. Repository-wide checks run through `kb check`.

Applying a Proposal changes the linked Draft and Proposal state in one Runtime transaction; the Publisher never accepts a Proposal ID or publishes Proposal content directly. After a canonical commit succeeds, the matching applied Proposal is finalized as merged, while an applied Proposal whose content no longer matches is stale. The commit contains only the published canonical path, even when unrelated files are already staged. The default message is generated from the entity type and ID; callers can supply a message. `Publisher.restore(path, revision)` validates historical schema and the complete prospective repository reference state before restoring a canonical file as a new commit. Heading and Mermaid style findings are returned as warnings during Restore; structural and reference errors still block it. Document and Term deletions are rejected when they leave dangling Collection references; unresolved Wiki Links remain allowed. Source deletion is blocked while Markdown refers to it, and Taxonomy Registries cannot be restored to an absent file. Runtime synchronization failures after a commit appear as warnings.

The Publisher and Git Manager remain service-level components; API routes and the Reference Hub are later phases. Phase 5 supplies the rebuildable index and usage services described below.

## Phase 5: Indexer + Search + Usage

`Indexer.full_rebuild()` reconstructs Document, Term, Alias, Taxonomy, Backlink, Evidence, and FTS5 indexes from canonical files in one SQLite transaction. A failed rebuild leaves the previous derived index intact. `Indexer.update_path()` updates one changed entity and refreshes affected relationships; `Publisher` attempts it after each successful publish and restore and reports failures as warnings.

`SearchService.search()` combines exact ID, title, alias, and FTS5 matches with Domain, Topic, Tag, Document Type, Review, Maintenance, Source, and Term filters. Document FTS results join usage statistics and receive a capped, small ranking boost; Term and Source results do not. CJK queries also use escaped literal substring matching against Document, Term, Source, and Evidence text. Taxonomy entries may declare aliases, which the Taxonomy Resolver uses to resolve alternate names. Unresolved and ambiguous wiki links do not create Backlinks. Usage cannot outrank exact, title, or alias matches.

`UsageService` records only `document_open` and `search_result_click`. It derives view counts, click counts, and last-viewed time in Runtime SQLite; a full rebuild recalculates those statistics from the retained event history. `recently_viewed()` and `frequently_viewed()` expose the corresponding document lists. These services are not yet exposed through API routes or a Reference Hub.

The complete local requirements are held in `docs/private/KnowledgeBase_v1_架构与Codex实施方案.md` and `docs/private/KnowledgeBase_系统需求与知识模型规范.md`; those private source files are intentionally ignored by Git.

## Phase 6: Import Pipeline

`ImportService.stage_paths()` accepts `.md` and `.pdf` files or directories, copies supported files into per-job staging, records SHA-256 hashes, detects canonical and same-job duplicates, and creates Document, Term, or Source candidates for review. A later Import Job can stage the same file again if it has not become canonical. Directory imports can suggest a Markdown/PDF bundle by matching their folder and filename; the relationship becomes confirmed only after an explicit association call. The legacy profile adds unreviewed and legacy maintenance defaults to imported Markdown Drafts.

Markdown needs valid canonical metadata before it can become a Document or Term Draft. ImportService uses the shared `CanonicalTargetResolver` for Document, Term, and Source target paths. Writing-style findings are retained on the Import Item for review and do not prevent draft creation. A new blank Document follows the same Draft workflow. A PDF is never converted into a Note: confirming it creates a Source Draft and copies the PDF into ignored `storage/papers/`. Existing Source matches are resolved deterministically by identifier and then title, or require explicit selection when ambiguous. `Publisher` checks a local PDF attachment before publishing its Source metadata, commits only the canonical YAML file, and attempts to refresh the Source index. Imports do not write canonical files directly and do not invoke AI.

The API and Review page support staging, review, and Draft creation. The `kb import` command stages arbitrary local paths for batch migration; production Compose can mount a read-only import directory at `/imports`.

## Phase 7: DeepSeek Gateway

`AIGateway` sends fixed task requests through the backend-only DeepSeek client. Each supported task declares a Pydantic JSON schema, Proposal kind, and the registries or writing standard it needs. The client uses configured timeout and bounded retries for transient transport failures; malformed responses are rejected before any Proposal is stored. `AIProposalService` binds validated results to the current Draft content hash and stores them through `ProposalService`. AI output never writes canonical files or invokes Git. The client is injectable, and `MockDeepSeekClient` supports offline tests.

The initial task registry supports metadata suggestions, Term detection, semantic format review, Document review, Term drafting, revision suggestions, and Evidence suggestions. The API key is read from a backend environment variable; it is not exposed to the frontend.

## Phase 8: Knowledge API

The FastAPI surface exposes canonical Document, Term, Source, Topic, and Search reads; Context Export; Draft and Proposal review; publishing through `Publisher`; Import workflows; AI Proposal requests; and Usage events and lists. Read endpoints consume the rebuildable SQLite indexes and resolve canonical content from the indexed knowledge path. Responses omit repository paths. Draft creation captures the canonical Git revision and target hash on the server, and Proposal application checks its linked Draft revision and base content hash.

Import requests accept relative paths under `storage/uploads/`; traversal and symbolic links are rejected. `kb import` accepts local files and directories for batch migration. AI requests require explicit `confirm_deepseek_transfer: true`, disclose that Draft content and the needed registry context will be sent to DeepSeek, and return only a validated Proposal. Metadata Suggestions are available from the Document editor and never apply themselves. Evidence Suggestions identify Draft claims needing evidence and recommend existing Source IDs from registry metadata; they do not generate quotes or locators and are not Evidence. Context Export supports `raw`, `reviewed`, and `verified` trust levels and the `research`, `teaching`, and `evidence` purposes. Verified claims require a human-approved Document and a Source whose metadata review status is `verified`; this is provisional traceability, not per-claim Evidence verification, and PaperSkillWork must not treat it as Evidence Verified. Presentation Annotation APIs are separate from canonical reads and exports. The API schema is available at `/openapi.json` and `/docs`.

## Phase 9: Reference Hub reading interface

Home uses reading and Git history summaries, and Search uses the structured filters from the indexed API. Library and Topics browse canonical Documents, Terms, and Sources. Review aggregates unreviewed and revision-needed entities, open Proposals, Import Items, unresolved or ambiguous Wiki Links, and stale visual annotations. Readers apply Runtime Presentation Annotations after Markdown rendering; Source pages do not support text annotations.

Document and Term pages render Markdown, KaTeX, Mermaid, wiki links, backlinks, detected unlinked mentions, and indexed citations. Source pages show metadata and related Documents and Terms. Runtime state remains behind the API; the browser does not read canonical files or access Git directly.

Markdown Documents and Terms have a small canonical formatting toolbar for emphasis, code, and math. Formatting edits Draft Markdown; highlight, color, and underline remain Runtime Presentation Annotations. Successful publication refreshes the Draft comparison base to the committed content. Canonical Markdown and YAML remain writable only through `Publisher`.

Document editors manage Source associations, inline citation candidates, and PaperSkill links; Source editors can associate a local PDF URI. Readers show citation and Evidence details alongside associated PaperSkill URLs; Evidence Suggestions remain suggestions and do not generate quotes or locators. Document and Source readers export and copy Context at `raw`, `reviewed`, or `verified` trust levels for `research`, `teaching`, or `evidence` purposes. `verified` remains provisional traceability based on human approval and Source metadata review, not per-claim Evidence verification; PaperSkillWork must not treat it as Evidence Verified. Browser multipart upload and per-claim Evidence review are outside this phase. Canonical Markdown and YAML remain writable only through `Publisher`.

## Phase 12: Legacy Migration + Deployment

`kb import <path...> --profile legacy` stages batches of local Markdown and PDFs through the existing Import Service without publishing canonical content. Review can edit staged Markdown, create legacy Drafts with `unreviewed` and `legacy` metadata, and confirm PDFs as Source Drafts. The Document editor can request a metadata Proposal after explicit DeepSeek consent; a human applies selected fields to the Draft and separately publishes through `Publisher`. Review includes stale Presentation Annotations and import item actions.

Production Compose builds a static Nginx Reference Hub and API image. Only the Hub port is published, on loopback by default; the backend remains inside the Compose network. Tailscale Serve or a WireGuard-only host binding provides private access. `scripts/backup.py` archives a Git bundle, a consistent SQLite backup, and `storage/`; it refuses to run when the Git worktree has tracked or untracked changes. Production uses `scripts/production-backup.sh` to wait for the shared `runtime/research.lock`, then stop the frontend and backend during the snapshot. The repository includes deployment and restore instructions, but actual server provisioning and migration of user-owned legacy files require the operator's host, network credentials, and input data.

## Phase 13: Collection Explorer + Unified Workspace

Collections are canonical YAML trees under `knowledge/collections/`. Their schema validates node IDs, section depth, duplicate membership, and references to existing canonical entities. Collection order and node order come from YAML positions and array order. Collection membership and node indexes are derived SQLite data rebuilt by the Indexer; `Unfiled` is the virtual view of Documents absent from every Collection, while `All Documents` and `Recent` also remain virtual views. Collection reading progress is Runtime state and does not modify canonical content.

Collection editing follows the regular Draft lifecycle. Explorer changes create or update a Collection Draft, and the Publisher validates and commits the resulting YAML. Adding a note inside a Collection creates a Document Draft and updates the Collection Draft; batch publishing validates the prospective combined state and writes both files in one Git commit, restoring the prior files and retaining Drafts if the operation fails. Global new notes do not require a Collection. SQLite schema version 2 adds a unique index on `(entity_type, entity_id)` for active Drafts. Draft creation uses create-or-get semantics, including when two connections race. Migration reports duplicate targets and leaves the existing rows intact instead of silently selecting a Draft.

`/documents/:id`, `/terms/:id`, and `/sources/:id` are the sole entity routes. Collection context is carried by the `collection` query parameter. The same `Workspace` route presents reading and editing modes inside one shell; its Explorer pane stays mounted while the selected entity changes. An `edit=1` query opens the full Draft editor on direct entry and is removed when returning to reading. The retired `/edit/:type/:id` route and separate Editor page are removed. `useWorkspaceDraft` owns the single current-content state, loads Canonical content and existing Drafts without creating a Draft on read, and creates a Draft on the first edit before autosaving. Reader inline block edits replace Markdown parser source ranges in place; full-source editing remains available for YAML and complex Markdown.

Reader selection tools share a toolbar. Formatting maps the selection to Markdown source and autosaves a Draft; Presentation Annotations remain in Runtime SQLite and do not change Markdown. Ask AI starts with the selected text, requires explicit consent before sending it, and stores the response as a Proposal. Applying a content or metadata Proposal checks the linked Draft revision and base hash, then updates the Draft and Proposal state in one Runtime transaction. A normal Publish marks an exact applied candidate merged; if the Draft changed after application, the Proposal becomes stale.

Metadata, AI assistance, publishing review, and conflict recovery use Workspace drawers. Opening publish review saves pending content, compares each Draft against current Canonical content, and runs either single-Draft preflight or one revision-paired batch preflight for Document + Collection publishing. The review shows a change summary and full diff before confirmation. A successful commit returns warnings through a shared publish outcome so an index refresh warning remains visible. Preflight validates without writing Canonical files; only the Publisher writes canonical Markdown and YAML. Annotation anchors continue to refer to published Canonical content, so editing an unpublished body does not silently rebase annotations. Document and Collection conflict recovery share the Draft compare, rebase, and discard APIs. Reload Canonical deletes the conflicting Draft before reading the latest Canonical content; rebase is a separate action that retains the Draft.

Explorer, Workspace editor, Reader, and page components are grouped under `frontend/src/explorer/`, `frontend/src/workspace/`, `frontend/src/reader/`, and `frontend/src/pages/`. Route and feature files compose these focused components; feature hooks own workflow state and controllers orchestrate those hooks. Frontend unit and integration tests run with Vitest and Testing Library, and backend behavior is covered by pytest. Phase 13 is complete and frozen after 13.5. Phase 14 adds Research discovery, Research Agent models, and scheduled literature searches.

Runtime Draft unmount cleanup only clears autosave timers and invalidates the current session. Internal Workspace and Explorer navigation and browser Back/Forward await a dirty Draft save and remain on the current route on save failure or conflict. Browser close warnings are active only while a Draft is dirty. Ordinary Discard is unavailable while saving or in Runtime/Canonical conflict; conflict drawers retain explicit resolution actions. Publish requires the reviewed revision for each Draft, including every entry in a batch, and batch preflight checks the prospective Document + Collection references without writes. Import, Draft APIs, and Publisher share `CanonicalTargetResolver`; repository duplicate-ID validation belongs to `kb check`, full index rebuild, and Publish validation. Restore validates its prospective repository reference state before committing and rolls back temporary file changes on failure. Resolver calls retain path, schema, slug, and containment checks without rescanning all canonical files. These are the final Phase 13 lifecycle and data-integrity rules; Phase 13 is frozen after 13.5, with no further subphases or cleanup work.

## Phase 14: Research Agent (implementation complete; production acceptance pending)

Research Profiles under `config/research/profiles/` and global Research settings under `config/research/research.yaml` are canonical YAML. ### Runtime and Provider pipeline

The Research pipeline uses offline-testable Provider adapters, deterministic normalization, deduplication and screening, bounded knowledge Context Packs, typed DeepSeek Analysis, atomic Candidate-capacity checks, a global process lock, and small SQLite transactions. Runs are recorded before external calls. Active Lens / Query / Provider streams are ordered by Lens priority and advance one bounded Provider page per stream per round. Eligible Works from a round are deduplicated and globally Pre-Ranked before Analysis and Candidate budgets are applied. A per-Run Provider circuit stops further requests to a provider after its failure threshold. Backlog scanning paginates past ineligible older Discoveries and gives eligible backlog a bounded per-Run analysis quota, so new high-ranked Works cannot indefinitely starve it. Only actual Analysis attempts consume the global budget: backlog Works removed by enrichment or deterministic eligibility checks release their unused capacity to new Works. Enrichment is followed by a focused deterministic recheck for canonical Source matches and changed include/exclude eligibility before Context construction or DeepSeek Analysis. Incomplete slices do not advance their watermarks; stale Runs and manual requests recover on a later tick. When AI Analysis is disabled, discovery, deterministic screening, metadata enrichment, Discovery persistence, and watermark progress continue without building a Context Pack, calling DeepSeek, or generating Candidates. Re-enabling AI processes up to 10 oldest eligible unanalyzed Discoveries per Run, subject to the configured analysis, Candidate, and Inbox budgets. When AI Analysis is enabled, reaching per-run analysis or Candidate budgets keeps the Run successful, records a warning, and leaves the active slices incomplete. Reaching Inbox capacity prevents another page request and leaves the active slices incomplete. Each scheduled tick handles at most one oldest manual request or one most-overdue scheduled Profile. The Web lifespan also coordinates one manual-only child process at a time. It calls `tools/research.py manual-tick` with the running Python, fixed repository/database paths, and an independent SQLite connection. `manual_tick()` and `tick()` reuse the same locked queue consumption and pipeline. Startup notification plus a 30-second fallback processes pending requests and safely retries lock contention; stale claims retain the existing 45-minute recovery condition. Shutdown terminates/reaps the executor, and startup failures before claiming persist a failed request and Run without overwriting active work. Request lookup and recent per-Profile request APIs associate each attempt with its Run. No automatic Profile or Term Discovery is triggered by this executor.

`tools/research.py` validates configuration without network calls and supports Profile, Runtime status, scheduled tick, direct diagnostic Run, and pending-conversion reconciliation commands. FastAPI and Research CLI Runs use the same `build_research_components` bootstrap for the Profile registry, normalized Research DeepSeek configuration, AI Gateway, KnowledgeReadService, CollectionService, ContextExportService, Providers, and Research service. Research Analysis has its own timeout-configured Gateway; the regular AI Proposal Gateway uses the general AI environment configuration and is unaffected by Research timeout settings.

The Research API exposes Profile controls, queued manual searches, Run inspection, Candidate filtering and detail, Shortlist with an optional note, note editing, Dismiss with an optional reason and note, Restore, Save Source, and Create Note. Restore checks the Profile's configured Inbox capacity atomically and remains available when the Profile is disabled; a full Inbox returns a conflict without changing the Candidate. Create Note checks Candidate detail for ambiguous Source matches before opening the form, while the server conversion check remains in place. Ambiguous Source detail identifies each candidate canonical Source and shows concrete conflicting identifier fields and values, or explains when ambiguity comes from multiple weak title/author/year matches. The UI opens the Source Workspace metadata drawer, where users can edit Source type, title, authors, year, DOI, arXiv ID, OpenAlex ID, URL, and advanced Zotero Key as Draft metadata; year and URL are buffered locally and validated before they update the Draft, while publishing still goes through Publisher. The Research page supports Profile creation or duplication through Draft/Publisher; Profile Defaults and Research Focus editing; temporary Focus and breadth controls; automatic-only Pause/Resume; Inbox capacity; manual search; Candidate reading, Shortlist notes, Dismiss, History, batch Inbox actions, Run inspection, and Source/Note Draft creation. Restoring from History keeps the user there, removes the Candidate from the list, and offers a direct Inbox action. New Research Focus entries need only a name and initial query; the system generates a unique technical identifier. Single-candidate Shortlist and Dismiss are immediate; bulk actions retain confirmation. Candidate cards keep the common actions and summarize related knowledge by count; Save Source is in Candidate detail. Candidate detail leads with the paper summary, why it matters, reading reason, related knowledge, and note. Shortlist, Dismiss, and notes are saved directly in Runtime; Save Source and Create Note enter the canonical knowledge base only after publishing. Dismissed status uses a neutral tone. Model relevance/novelty signals and the recommended ranking score are inside Technical provenance → Model signals, both collapsed by default, with a calibration note. Run inspection leads with status, time, duration, results checked, new Works, surfaced Candidates, and any issues; provider metrics and effective configuration are under collapsed Technical details. Profile summaries include pending and claimed manual-queue counts. Context materialization is bounded by the configured card limit; selected-context retrieval searches only the Profile's selected Documents and Collection members. Pinned selectors filter locally by title or ID without changing selection. Each Candidate has one primary analyzed Lens; other Lens hits remain Discovery provenance. AI-suggested Collection and Section values appear in Candidate detail; a Collection is preselected only when valid, and a Section only when its title matches uniquely.

### Search Streams and catch-up

A Search Stream is keyed by Profile, Lens, Provider, and normalized Query. A new Query key starts from `initial_lookback_days`. When an active stream has a stale watermark, a scheduled Run bounds its catch-up to `max_catchup_days` and persists that lower boundary before calling a Provider. An incomplete slice retries from the same boundary instead of moving forward as time passes. Re-enabling a Profile, Lens, Provider, or automatic schedule does not require a publish-time review. Pause/Resume keeps its explicit catch-up or from-now choice and its watermark-skip audit; Resume without a custom duration defaults to the Profile's `max_catchup_days`. Pause blocks scheduled Research only; manual Search Now and queued manual work remain available while the Profile itself is enabled. Every manual Run, including direct diagnostic Runs and queued runs without a date range, may read scheduled progress but never advances scheduled watermarks. Historical manual date ranges remain independent.

Lens include/exclude terms, Profile exclude terms, breadth, and Knowledge Context settings affect future Runs. The system does not automatically re-screen or re-analyze history already covered by a watermark. Use Search Now with a historical date range to apply changed policy to past papers.

### Source and Note conversion

Save Source matches canonical Sources by normalized DOI, arXiv ID, or OpenAlex ID, then by normalized title, first author, and year within ±1. Weak matching excludes Sources with conflicting strong identifiers. Multiple weak matches or conflicting strong-identifier matches are ambiguous: screening retains the Work with an `ambiguous_existing_source` warning, while Save Source and Create Note reject conversion until the canonical Source metadata is resolved.

If Save Source creates a Draft, only Candidates with an explicit pending Source conversion intent for a published Draft are finalized.
