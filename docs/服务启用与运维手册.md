# KnowledgeBase 完整服务启用与运维手册

本手册说明如何在 Windows 本机完整验收 KnowledgeBase，以及如何在私有 Linux 服务器上正式运行。正式环境推荐使用生产版 Docker Compose，并通过 Tailscale 或其他受控 VPN 访问。

> 当前应用没有内置登录、用户账户或角色权限。生产 Compose 默认只监听服务器本机地址；不要把 8000 或 8080 端口直接开放到公网。远程访问必须由 Tailscale ACL、WireGuard 防火墙或同等的私有网络访问控制保护。

## 1. 先选运行方式

| 方式 | 用途 | 地址 | 建议 |
| --- | --- | --- | --- |
| Windows 一键验收 | 本机运行后端和生产构建预览 | `http://127.0.0.1:4173` | 本机试用、验收 |
| 开发版 Compose | 本机运行 Vite 开发服务器和后端 | `http://127.0.0.1:5173` | 开发和调试 |
| 生产版 Compose | Linux 私有服务器运行 Nginx 和后端 | 默认 `http://127.0.0.1:8080` | 长期使用 |

生产版 Compose 不会向主机发布后端 8000 端口。Nginx 代理 API 请求，后端只在 Compose 内部网络可用。Windows 一键脚本是本机启动入口，不是带登录和公网防护的服务器部署方案。

## 2. Windows 本机完整验收

在仓库根目录打开 PowerShell。首次创建本机 Python 环境并安装后端依赖：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend/requirements-dev.txt
```

`build-and-open.ps1` 会在前端依赖缺失时安装依赖、构建前端、检查并启动本机后端，然后打开预览页面：

```powershell
.\scripts\build-and-open.ps1
```

默认地址是前端 `http://127.0.0.1:4173`、后端 `http://127.0.0.1:8000`。第一次运行后，在另一个 PowerShell 窗口建立搜索和关系索引：

```powershell
.\.venv\Scripts\python.exe tools/kb.py rebuild
.\.venv\Scripts\python.exe tools/kb.py check
```

前端预览端口被占用时可改用其他端口，例如：

```powershell
.\scripts\build-and-open.ps1 -Port 4273
```

### 8000 端口已有旧后端时

脚本检测到旧版或不兼容服务时会停止启动前端，并显示：

```text
Port 8000 is running an incompatible/outdated KnowledgeBase backend. Stop the old backend and run this script again.
```

先查看监听进程及其命令行，确认它确实是旧 KnowledgeBase 后端：

```powershell
$listener = Get-NetTCPConnection -LocalPort 8000 -State Listen -ErrorAction SilentlyContinue |
  Select-Object -First 1
$listener
Get-CimInstance Win32_Process -Filter "ProcessId = $($listener.OwningProcess)" |
  Select-Object ProcessId, Name, CommandLine
```

如果 `$listener` 没有结果，8000 当前没有监听服务，跳过停止进程的步骤，直接重新运行启动脚本。

仅在端口确有监听、并且确认进程是旧 KnowledgeBase 后端后，再停止它并重新运行启动脚本：

```powershell
Stop-Process -Id $listener.OwningProcess -Confirm
.\scripts\build-and-open.ps1
```

不要停止来源不明或仍在使用的进程。后端和预览日志分别写入 `runtime/backend-local/` 与 `runtime/frontend-preview/`。本机脚本负责启动和验收，不负责 Windows 登录后的自动常驻；需要长期运行时使用生产部署方式。

## 3. 本机 Docker 开发服务

安装并启动 Docker Desktop，在仓库根目录执行：

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
docker compose config -q
docker compose up -d --build
docker compose ps
```

第一次启动后构建索引：

```powershell
docker compose exec backend python /workspace/tools/kb.py rebuild
docker compose exec backend python /workspace/tools/kb.py check
```

浏览器访问 `http://127.0.0.1:5173`。开发服务只绑定本机地址。查看日志：

```powershell
docker compose logs --tail=100 backend frontend
```

停止容器：

```powershell
docker compose down
```

仓库中的 `runtime/` 和 `storage/` 使用主机目录保存，停止容器不会清空这些目录。不要手动删除其中的数据库、PDF 或暂存文件。

## 4. Linux 私有服务器正式部署

### 4.1 准备服务器和仓库

准备一台可运行 Docker Engine 与 Docker Compose v2 的 Linux 服务器，并确保部署账号可以访问私有 Git 仓库和运行 Docker。建议先确认仓库中的 Canonical 内容已提交并推送，再从私有远端克隆：

```sh
git clone <私有仓库地址> /srv/KnowledgeBase
cd /srv/KnowledgeBase
cp .env.example .env
```

部署目录需要由负责运行服务的账号管理。生产 Compose 会把整个仓库挂载给后端容器，Publisher 通过 Git 在 `knowledge/` 中提交正式内容。

#### 已有 root 运行部署的一次性权限迁移

此步骤只适用于旧版 root 运行的 Backend 已在服务器上留下 root 所有的文件；全新部署不需要执行。切换到部署账号运行的新 Backend 前，先安排维护窗口并保留备份；如果启用了 Research timer，先停止 timer，再运行生产备份入口（它会等待当前 Research Run 完成），随后停止 Frontend 和 Backend。以部署账号检查：

```sh
cd /srv/KnowledgeBase
id -u
id -g
find .git runtime storage -user root -print
```

只有当列出的文件确实由旧 KnowledgeBase 容器产生，而且整个部署目录及其备份/导入目录都应归当前部署账号管理时，才一次性执行：

```sh
sudo chown -R "$(id -u):$(id -g)" \
  /srv/KnowledgeBase \
  /srv/KnowledgeBase-backups \
  /srv/KnowledgeBase-imports
git status
```

如果使用了自定义路径，请替换成实际目录。确认 `git status` 正常后再启动新版服务。不要把递归改所有权操作加入入口脚本，也不要在每次启动时自动修复权限。

### 4.2 设置私有配置

编辑 `.env`，至少检查以下项目：

```dotenv
KB_HTTP_BIND=127.0.0.1
KB_HTTP_PORT=8080
KB_IMPORT_DIRECTORY=/srv/KnowledgeBase-imports
KB_BACKUP_DIRECTORY=/srv/KnowledgeBase-backups
KB_GIT_USER_NAME=KnowledgeBase
KB_GIT_USER_EMAIL=knowledgebase@localhost
KB_RUNTIME_UID=1000
KB_RUNTIME_GID=1000
```

以负责部署的 Linux 账号执行 `id -u` 和 `id -g`，并将输出分别填入 `KB_RUNTIME_UID` 与 `KB_RUNTIME_GID`。生产 Backend 会以此 UID/GID 运行，避免 Publisher 在挂载的仓库、Runtime 数据库和 Storage 中留下 root 所有的文件。

为导入和备份创建主机目录，并限制配置文件权限：

```sh
mkdir -p /srv/KnowledgeBase-imports /srv/KnowledgeBase-backups
chmod 700 /srv/KnowledgeBase-imports /srv/KnowledgeBase-backups
chmod 600 .env
```

`KB_IMPORT_DIRECTORY` 是供服务器批量迁移使用的只读目录，会挂载到容器的 `/imports`。浏览器上传的 Markdown/PDF 会进入仓库下的临时上传目录，并经过 ImportService 暂存。`KB_BACKUP_DIRECTORY` 应位于仓库之外，并定期复制到另一处受保护的存储。

如果要使用 AI 功能，将 DeepSeek 密钥写入 `.env` 的 `DEEPSEEK_API_KEY`。密钥留空时，阅读、编辑、导入、审阅和发布仍可使用，AI Proposal 请求不可用。不要把真实密钥提交到 Git、粘贴到公开日志或写进前端配置。

`.env` 中的 `KNOWLEDGE_REPO_PATH` 和 `DATABASE_PATH` 在生产 Compose 中分别固定为 `/workspace` 与 `/workspace/runtime/knowledge.db`；不要为生产部署改成容器之外的路径。

### 4.3 验证配置并启动

在仓库根目录运行：

```sh
docker compose --env-file .env -f docker-compose.production.yml config -q
docker compose --env-file .env -f docker-compose.production.yml up -d --build
docker compose --env-file .env -f docker-compose.production.yml ps
docker compose --env-file .env -f docker-compose.production.yml exec -T backend id
```

确认容器输出的 UID/GID 与部署账号一致后再使用 Publisher。Backend 会在 `/tmp/knowledgebase-home` 创建 Git 全局配置目录。

首次启动会创建 Runtime 数据库，但不会自动从 Canonical 文件重建搜索索引；因此第一次部署必须执行：

```sh
docker compose --env-file .env -f docker-compose.production.yml exec backend \
  python /workspace/tools/kb.py rebuild
docker compose --env-file .env -f docker-compose.production.yml exec backend \
  python /workspace/tools/kb.py check
```

确认 Backend 和 Frontend 容器均处于运行/健康状态，页面及 API 可访问：

```sh
curl -fsS http://127.0.0.1:8080/ >/dev/null
curl -fsS http://127.0.0.1:8080/openapi.json >/dev/null
for path in api/documents api/terms api/sources api/proposals api/imports api/review/link-issues api/annotations/stale; do
  curl -fsS "http://127.0.0.1:8080/$path" >/dev/null || exit 1
done
```

在服务器本机浏览 `http://127.0.0.1:8080`。生产服务默认只接受服务器本机连接；从其他设备访问时，先配置私有 VPN。使用 Tailscale 时，保持 loopback 绑定，可参考 [`docs/DEPLOYMENT.md`](DEPLOYMENT.md) 的 Tailscale Serve 步骤，并用 Tailscale ACL 限制成员。使用 WireGuard 时，按部署文档将 `KB_HTTP_BIND` 设为服务器的 WireGuard 接口地址，并只允许 VPN 网卡访问该端口。不要使用 Funnel，也不要把 `KB_HTTP_BIND` 改成 `0.0.0.0` 暴露到公网。

## 5. 初次数据导入和日常使用

### 已有 Canonical 知识

已提交在 `knowledge/` 的 Markdown/YAML 是正式知识源。首次部署或人工直接修改 Canonical 文件后，运行 `kb rebuild` 更新搜索、关系和引用索引；应用内 Publisher 发布成功后会尝试增量更新索引。

### 从电脑上传 Markdown/PDF

1. 打开 Review → Import Review。
2. 选择文件或拖入多个 `.md` / `.pdf`，再选择 `Standard` 或 `Legacy`。
3. 上传只会建立 Import Job 并暂存，不会直接发布 Canonical 内容。
4. `Standard` Markdown 需要先补齐并检查有效 Frontmatter，再从 Review 创建 Draft。`Legacy` 旧笔记可以没有 KnowledgeBase Frontmatter；创建 Draft 时会生成最小元数据、标记为 `unreviewed` / `legacy` 并保留原正文，之后请检查生成字段。
5. PDF 需要人工确认 Source 元数据；PDF 不会自动生成 Document。
6. 在 Editor 检查 Draft 后，使用 Publish 写入 Canonical 并生成 Git commit。

`Legacy` 会为旧笔记应用 `unreviewed` 与 `legacy` 元数据默认值；即使原文件没有 KnowledgeBase Frontmatter，也能在创建 Draft 时生成最小元数据并保留正文。所有导入都需要人工审阅；使用 AI 生成 Proposal 时，界面会要求明确同意发送所需 Draft 和 Registry 上下文。

### 服务器批量迁移

将迁移文件放在 `KB_IMPORT_DIRECTORY` 指定的主机目录中，然后在服务器运行：

```sh
docker compose --env-file .env -f docker-compose.production.yml exec backend \
  python /workspace/tools/kb.py import /imports --profile legacy
```

命令只做暂存。随后在 Review 中检查 Import Items、创建 Draft 或确认 PDF Source，并单独 Publish。更完整的字段和审阅规则见 [`docs/IMPORT_WORKFLOW.md`](IMPORT_WORKFLOW.md)。

### Git 发布与同步

在录入私人 Canonical 内容、使用 Publisher 或推送提交前，先在服务器仓库执行 `git remote -v` 并确认生产远端的公开/私有策略。Canonical 可能含有个人或其他私密内容时，production 必须使用私有 Git remote；Tailscale 或其他 VPN 只限制应用服务器的访问，不会让公开托管的 Git 仓库变成私有。不要把私人 Canonical push 到 public remote。

每次 Publish 会由 Publisher 在服务器仓库创建 Canonical Git commit，不会自动推送到远端。若配置了 Git remote，确认提交内容和远端隐私策略后在服务器仓库执行 `git push`，以便其他工作副本和代码部署保留相同历史。不要在服务运行时手工覆盖 `knowledge/` 文件；如需直接编辑，先备份并通过 Git 管理，再运行 `kb check` 与 `kb rebuild`。

## 6. 日常启停、更新与日志

查看状态和日志：

```sh
docker compose --env-file .env -f docker-compose.production.yml ps
docker compose --env-file .env -f docker-compose.production.yml logs --tail=100 backend frontend
```

重启服务：

```sh
docker compose --env-file .env -f docker-compose.production.yml restart
```

升级前先停止 Research timer，再用生产备份入口完成快照。备份入口会等待正在运行的 Research Run 完成，因此不要在它结束前手工杀掉 Research service。然后暂停 Web 服务，再更新代码、构建镜像并执行检查；只有两项检查都成功后才重新启用 timer：

```sh
sudo systemctl stop knowledgebase-research.timer
./scripts/production-backup.sh
docker compose --env-file .env -f docker-compose.production.yml stop frontend backend
git pull --ff-only
docker compose --env-file .env -f docker-compose.production.yml config -q
docker compose --env-file .env -f docker-compose.production.yml up -d --build
docker compose --env-file .env -f docker-compose.production.yml exec -T backend python /workspace/tools/kb.py check
docker compose --env-file .env -f docker-compose.production.yml exec -T backend python /workspace/tools/research.py check
sudo systemctl start knowledgebase-research.timer
docker compose --env-file .env -f docker-compose.production.yml ps
```

如果任一检查失败，先保持 Research timer 停止并处理问题，再启动 timer。该顺序可避免 Research timer 在 `git pull` 与 Docker rebuild 之间用新 Checkout 代码操作共享 Runtime 数据库。

Compose 服务配置了 `restart: unless-stopped`。还需确保服务器 Docker 服务会随系统启动；使用 systemd 的 Linux 主机可执行 `sudo systemctl enable --now docker`。停止服务可以使用：

```sh
docker compose --env-file .env -f docker-compose.production.yml stop
```

停止并移除容器（不删除仓库中的 Runtime/Storage 主机目录）：

```sh
docker compose --env-file .env -f docker-compose.production.yml down
```

不要使用 `docker compose down -v` 作为日常停机命令，也不要删除 `runtime/` 或 `storage/`。

## 7. 备份与恢复

Runtime SQLite 保存 Draft、Proposal、Import Job、使用统计和阅读标注；`storage/` 保存 PDF 与暂存导入。Git 历史保存 Canonical 知识。三部分都需要保护。

确认整个 Git worktree 干净（包括 `config/research/profiles/` 与 `config/research/research.yaml`）后，运行备份：

```sh
./scripts/production-backup.sh
```

生产备份脚本先使用 Linux 主机的 `flock` 等待共享的 `runtime/research.lock`，最长等待 45 分钟。正在运行的 Research Run 可以自然完成；备份持有锁期间，新 tick 会跳过。若等待超时，脚本会在停止服务前退出。取得锁后，脚本短暂停止 Frontend 和 Backend，再使用同一生产 Compose 配置启动一次性 Backend 完成快照，并在成功、失败或收到中断信号后重新启动服务。备份归档包含 Git bundle、Runtime SQLite 快照、`storage/` 归档和清单；不包含 `.env` 或 DeepSeek 密钥。脚本会在 Git worktree 有已跟踪或未跟踪的改动时拒绝备份；被 Git 忽略的 `runtime/`、`storage/` 和 `.env` 不会触发拒绝。确认备份文件已生成，并定期将其复制到第二个受保护位置。通过受信任的密码管理器或 Secret Manager 单独保存必要的 `.env` 配置，不要把密钥放进备份归档或 Git。首次启用后就应安排定期备份，并周期性演练恢复。

Linux 主机可用部署账号设置每日凌晨 2 点备份，例如在 `crontab -e` 中添加：

```cron
0 2 * * * cd /srv/KnowledgeBase && ./scripts/production-backup.sh >> "$HOME/.local/state/knowledgebase/backup.log" 2>&1
```

添加定时任务前，以同一部署账号创建日志目录：`mkdir -p "$HOME/.local/state/knowledgebase"`。定期轮换该日志文件。

恢复时使用一个新的、空的目录，先停止服务并保留原部署。参考 [`docs/DEPLOYMENT.md`](DEPLOYMENT.md) 中的完整恢复命令；恢复 Git bundle、`runtime/knowledge.db` 和 `storage.tar.gz` 后，安全重建 `.env`，运行 `kb check` 与 `kb rebuild`，再启动 Compose。bundle 克隆会暂时把 `origin` 指向解包目录中的临时 bundle；在删除暂存目录或执行 Git 同步前，按部署文档检查并替换为真实私有 remote，或在生产不使用远端时移除这个临时 `origin`。不要把归档直接覆盖到正在运行的仓库。

## 8. 常见问题

| 现象 | 处理方式 |
| --- | --- |
| 本机脚本报 8000 端口不兼容 | 按“8000 端口已有旧后端时”检查进程命令行，确认后停止旧后端，再运行脚本。 |
| 页面能打开但知识列表为空 | 第一次启动或人工修改 Canonical 后运行 `python /workspace/tools/kb.py rebuild`。 |
| Backend 容器不健康 | 查看 `docker compose ... logs backend`；确认 Docker 构建包含当前 `backend/requirements.txt`，必要时 `up -d --build`。 |
| 浏览器无法上传 `.md` / `.pdf` | 确认部署的是新构建的后端镜像，文件扩展名为 `.md` 或 `.pdf`，然后检查 Backend 日志。 |
| AI Proposal 请求失败 | 检查后端的 `DEEPSEEK_API_KEY` 和模型配置；密钥只应配置在服务器环境。 |
| Publish 失败 | 查看 Editor 错误，确认仓库可写、Git 用户名和邮箱有效，并按 Draft 的冲突提示处理。 |
| 远程电脑无法访问默认地址 | 默认只绑定服务器本机。配置 Tailscale/WireGuard 和访问规则；不要直接开放公网端口。 |
| 备份命令拒绝运行 | 先通过 Git 处理 `knowledge/` 下未提交的 Canonical 更改，再重试。 |

- [ ] 首次 `kb rebuild` 完成，`kb check` 无错误。

- [ ] 已用 Review 完成一份 Markdown 和一份 PDF 的暂存与人工审阅流程。
- [ ] 已确认 Publish 会生成 Git commit，并确定如何推送或备份这些提交。

- [ ] `.env`、API 密钥、Runtime 数据库、Storage 文件都有明确的访问和备份权限。
