# KnowledgeBase 生产服务器版本更新与验收手册

> 用途：日后每次将开发仓库的 `main` 更新到已经运行的单用户 KnowledgeBase 服务器时，按此文档执行，**不针对某次固定提交**。
>
> 适用现有环境：Linux、部署账号 `agent`、仓库 `/srv/KnowledgeBase`、生产 Compose、Research 的主机 systemd Timer、Tailscale 私有访问。`agent` 无 sudo 权限；所有 `systemctl stop/start` 均由 **root 的另一终端**执行。
>
> 原则：保护生产 Publisher 本地 Git 提交、Canonical、Runtime SQLite、`storage/`；严格 **备份 → 升级代码 → 新 Backend 启动迁移 → 检查索引/服务 → 人工工作流 → 恢复 Timer**。任何失败停止后续步骤；不使用 `reset --hard`、`rebase`、`down -v`、清库或覆盖运行中的数据库。

## 0. 一次更新的放行前提（开发机 / GitHub）

在碰生产服务器前，先确认：

- 目标提交在 GitHub `main`，明确其**完整 SHA**，且该 SHA 对应的 CI 已 `success`；不是仅观察旧提交的成功 CI。
- 对照本次代码范围审查：数据库迁移、Research Worker 和 Web Backend 对共享 Runtime 的兼容性、Canonical 变更、前端真实交互。
- 重要回归测试必须通过；CI 不能替代浏览器可视化验收。
- 无尚未修复的部署阻断问题。若已知公式、高亮、核心提案流程等存在渲染/工作流错误，先修复再部署。
- 生产 Remote 的 Git 仓库可见性符合实际数据保密要求；Tailscale **不会**保护公开 GitHub 仓库中被推送的私人笔记。

**每次由操作者填写并记录：**

```text
目标 SHA：<本次 GitHub main 的 40 位 SHA>
本次 CI：<GitHub Actions 成功运行 URL>
变更类型：<仅前端 / 后端 / Runtime migration / Research>
升级前服务器 SHA：<步骤 1 输出>
备份文件及 SHA256：<步骤 3 输出>
迁移前 / 后 Runtime schema：<步骤 1 / 步骤 6 输出>
操作者和验收日期：<记录>
```

预期：`agent`、`main`、Git 干净、Backend 正常，旧 Runtime 可读取，存储空间充足。`knowledgebase-research.service` 在非运行时 `inactive` 是正常的。若已有冲突、未提交改动或数据库损坏，**先停止升级**。

## 2. root：停止自动 Research

使用有管理权限的 root 会话，不要在 `agent` 中反复尝试 `sudo`。

```bash
systemctl stop knowledgebase-research.timer
systemctl is-active knowledgebase-research.timer || true
systemctl is-active knowledgebase-research.service || true
```

预期两项 `inactive`。Timer 停止不会强行杀死已在运行的 Research service；如果 service 仍 `active`，等待其自然完成再继续，备份脚本还有 `flock` 协调。

## 3. agent：正式备份、验证快照

先运行生产自带备份入口：

```bash
cd /srv/KnowledgeBase
./scripts/production-backup.sh
```

预期输出 `Created /backups/knowledgebase-<UTC时间戳>.tar.gz (...)`。**注意该脚本在备份前暂停 Backend/Frontend，结束时重新启动旧版服务**，所以后续必须再停止它们。归档包含 Git bundle、Runtime SQLite 快照、`storage.tar.gz` 和 manifest；**不包含 `.env`**。

在 `agent` 终端执行以下**完整独立脚本**，不要将其中的 `ARCHIVE`、`TMP` 等变量拆开到不同的 `bash <<'BASH'` 会话中：

```bash
cd /srv/KnowledgeBase

bash <<'BASH'
set -Eeuo pipefail
BACKUP_DIR='/srv/KnowledgeBase-backups'  # 如果 .env 的 KB_BACKUP_DIRECTORY 已更改，请修改这里
OLD_HEAD="$(git rev-parse HEAD)"
TMP="$(mktemp -d)"
trap 'rm -rf "$TMP"' EXIT

ARCHIVE="$(find "$BACKUP_DIR" -maxdepth 1 -type f -name 'knowledgebase-*.tar.gz' -printf '%T@ %p\n' | sort -nr | head -n1 | cut -d' ' -f2-)"
test -n "$ARCHIVE" && test -s "$ARCHIVE"
# 必须核对本次输出的备份名称/时间，不要误用旧备份
echo "Archive: $ARCHIVE"
tar -tzf "$ARCHIVE" >/dev/null
tar -xzf "$ARCHIVE" -C "$TMP" \
  knowledge.bundle runtime/knowledge.db storage.tar.gz manifest.json

git bundle verify "$TMP/knowledge.bundle"
git bundle list-heads "$TMP/knowledge.bundle" | grep -F "$OLD_HEAD" >/dev/null
tar -tzf "$TMP/storage.tar.gz" >/dev/null
python3 - "$TMP/runtime/knowledge.db" <<'PY'
import sqlite3, sys
from pathlib import Path
p = Path(sys.argv[1]).resolve()
c = sqlite3.connect(p.as_uri() + '?mode=ro', uri=True)
print('Backup schema:', c.execute('PRAGMA user_version').fetchone()[0])
check = c.execute('PRAGMA integrity_check').fetchone()[0]
print('Backup integrity:', check)
assert check == 'ok'
c.close()
PY
sha256sum "$ARCHIVE"
echo 'BACKUP VERIFIED: Git history + Runtime SQLite + storage archive'
BASH
```

验收：Git bundle 的 heads 包含旧生产 HEAD；SQLite `integrity_check: ok`；`storage` 可展开。**仅存在归档文件而未验证，不能视为备份通过。** 归档在本机生成后，应另存到第二个受保护位置；`.env`/密钥通过独立 Secret 管理渠道备份。

## 4. agent：Git 安全升级（保留 Publisher 提交）

此步骤修改代码、停止 Web；务必已完成上述备份验证和 Timer 停止。**每次修改下面的 `REVIEWED_SHA`，不可长期沿用示例 SHA。**

```bash
cd /srv/KnowledgeBase

bash <<'BASH'
set -Eeuo pipefail
COMPOSE=(docker compose --env-file .env -f docker-compose.production.yml)
REVIEWED_SHA='<填写本次CI通过且人工审核的40位main提交SHA>'

test "$REVIEWED_SHA" != '<填写本次CI通过且人工审核的40位main提交SHA>'
test "$(git branch --show-current)" = main
test -z "$(git status --porcelain)"
if systemctl is-active --quiet knowledgebase-research.timer || \
   systemctl is-active --quiet knowledgebase-research.service; then
  echo 'ERROR: Research timer/service still active'; exit 1
fi

OLD_HEAD="$(git rev-parse HEAD)"
git fetch origin main
TARGET_HEAD="$(git rev-parse refs/remotes/origin/main)"
echo "Old production: $OLD_HEAD"
echo "Fetched target: $TARGET_HEAD"
test "$TARGET_HEAD" = "$REVIEWED_SHA" || {
  echo 'ERROR: origin/main differs from reviewed CI SHA'; exit 1;
}

"${COMPOSE[@]}" stop frontend backend
if ! git merge-base --is-ancestor "$TARGET_HEAD" HEAD; then
  git merge --no-edit "$TARGET_HEAD"
fi

git merge-base --is-ancestor "$OLD_HEAD" HEAD
git merge-base --is-ancestor "$TARGET_HEAD" HEAD
test -z "$(git status --porcelain)"

git log --oneline --graph -12
"${COMPOSE[@]}" config -q
"${COMPOSE[@]}" build backend frontend

echo "Production HEAD: $(git rev-parse HEAD)"
echo "Preserved old HEAD: $OLD_HEAD"
echo "Included target: $TARGET_HEAD"
echo 'CODE UPGRADE + IMAGE BUILD: PASS; database migration not run by this step'
BASH
```

预期：两条祖先检查全部通过，Git 干净，镜像构建成功。生产 HEAD **可能是一个新的 merge commit**，不必等于目标 SHA。若 `git merge` 冲突，停止执行；**不可**重置服务器到 `origin/main`，不可强制覆盖 `knowledge/`。仅在理解 Publisher 与上游双方改动后人工处理。

## 5. agent：仅启动新版 Backend，自动迁移 Runtime

**启动新版 Backend 本身可能执行数据库 schema migration。** 再次确认步骤 3 的备份有效。不要先运行 Research tick 或新旧代码混合写入同一数据库。

```bash
cd /srv/KnowledgeBase

bash <<'BASH'
set -Eeuo pipefail
COMPOSE=(docker compose --env-file .env -f docker-compose.production.yml)
"${COMPOSE[@]}" up -d backend
CID="$("${COMPOSE[@]}" ps -q backend)"
test -n "$CID"
HEALTH='unknown'
for i in $(seq 1 40); do
  HEALTH="$(docker inspect -f '{{if .State.Health}}{{.State.Health.Status}}{{else}}no-healthcheck{{end}}' "$CID")"
  if [ "$HEALTH" = healthy ]; then break; fi
  if [ "$HEALTH" = unhealthy ]; then break; fi
  sleep 3
done
if [ "$HEALTH" != healthy ]; then
  "${COMPOSE[@]}" logs --tail=120 backend
  echo "ERROR: backend health=$HEALTH"; exit 1
fi
"${COMPOSE[@]}" exec -T backend python - <<'PY'
import sqlite3
from backend.app.db.migrations import CURRENT_SCHEMA_VERSION
path = 'file:/workspace/runtime/knowledge.db?mode=ro'
c = sqlite3.connect(path, uri=True)
version = c.execute('PRAGMA user_version').fetchone()[0]
check = c.execute('PRAGMA integrity_check').fetchone()[0]
print('Expected Runtime schema:', CURRENT_SCHEMA_VERSION)
print('Actual Runtime schema:', version)
print('SQLite integrity:', check)
assert version == CURRENT_SCHEMA_VERSION
assert check == 'ok'
c.close()
PY
"${COMPOSE[@]}" exec -T backend python /workspace/tools/kb.py check
"${COMPOSE[@]}" exec -T backend python /workspace/tools/kb.py rebuild
"${COMPOSE[@]}" exec -T backend python /workspace/tools/research.py check
"${COMPOSE[@]}" exec -T backend python /workspace/tools/research.py status

echo 'BACKEND / MIGRATION / CANONICAL / INDEX / RESEARCH CHECK: PASS'
BASH
```

预期：Backend `healthy`，schema 等于新版代码的 `CURRENT_SCHEMA_VERSION`，SQLite integrity `ok`，`kb check` 和 `kb rebuild` 成功，Research 配置正常。`kb rebuild` 只重建衍生索引，不代表可以清空 Runtime。**若 migration 报错，保留现场日志及升级前备份，不要用旧后端直接操作已迁移数据库。**

## 6. agent：旧快照与升级后持久化记录对比

此命令是**只读检查**。行数一致并不完全证明数据内容一致，但能发现明显的丢表、丢记录。不同版本如果确有正式数据清理迁移，应先阅读迁移说明，再人工批准差异。

```bash
cd /srv/KnowledgeBase

python3 - <<'PY'
import sqlite3, tarfile, tempfile, shutil
from pathlib import Path

backup_dir = Path('/srv/KnowledgeBase-backups')  # 如有定制请改路径
archives = sorted(backup_dir.glob('knowledgebase-*.tar.gz'), key=lambda p: p.stat().st_mtime)
assert archives, 'No backup archives found'
archive = archives[-1]
print('Compare against:', archive)
tables = (
    'drafts', 'proposals', 'usage_events', 'import_jobs', 'import_items',
    'presentation_annotations', 'research_works', 'research_discoveries',
    'research_candidates', 'research_runs', 'term_candidates',
)

def counts(db):
    existing = {r[0] for r in db.execute("SELECT name FROM sqlite_master WHERE type='table'")}
    return {table: db.execute(f'SELECT COUNT(*) FROM {table}').fetchone()[0]
            for table in tables if table in existing}

with tempfile.TemporaryDirectory(prefix='kb-audit-') as temp:
    p = Path(temp) / 'before.db'
    with tarfile.open(archive, 'r:gz') as tar:
        source = tar.extractfile('runtime/knowledge.db')
        assert source is not None
        with source, p.open('wb') as dest: shutil.copyfileobj(source, dest)
    old = sqlite3.connect(p.resolve().as_uri() + '?mode=ro', uri=True)
    newpath = Path('runtime/knowledge.db').resolve()
    new = sqlite3.connect(newpath.as_uri() + '?mode=ro', uri=True)
    try:
        before, after = counts(old), counts(new)
        for table, n in before.items():
            assert table in after, f'Missing persistent table: {table}'
            print(f'{table}: {n} -> {after[table]}')
            assert after[table] >= n, f'Rows decreased in {table}: {n} -> {after[table]}'
        print('Persistent table counts: PASS')
    finally:
        old.close(); new.close()
PY
```

**选取归档规则：**此处默认按时间选择最新备份。若升级过程中又执行了第二次备份，必须将对照文件改为**本次升级前**的那份，避免比较对象错误。

## 9. 浏览器人工验收（受控 Tailscale 地址）

使用真实浏览器访问；先测试**不破坏正式记录**的读取流程，再测试写入流程。根据本次提交增加专项测试。

| 工作流 | 操作及预期 |
|---|---|
| Home / 导航 | Summary、Research 状态正常；切换页签和刷新没有异常重复加载 |
| Library | Documents、Sources、Import 列表和数量正确；已有数据可打开 |
| Reader / Workspace | 旧文档可阅读；Markdown、代码、Mermaid、数学公式、目录正常；Draft 改动保存与保护正常 |
| Markdown 格式 | `==高亮==`、`<mark>`、受限颜色 `span` 正常；**必须单独肉眼检查 KaTeX 分式、上下标、求和符号、矩阵是否错位**；危险 HTML 不执行 |
| 导入标题 | 在 Import Review 中给可丢弃 Markdown 修改标题；创建 Draft 后 YAML `title` 正确；不应擅自更改 ID / 正文 H1 |
| Terms / Candidate | 术语识别结果、Evidence 摘录、现有 Term 关联操作正常 |
| Term Proposal | 打开之前已有的 Term Draft → AI 审阅 → 看到已生成 Proposal → Apply to Draft → 正文出现 → 保存；不得为了验收反复付费调用 AI |
| Term 再生成（仅必要时） | 从 Candidate 首次创建及**重新打开 Draft**两个入口都应保留 Candidate Evidence 上下文，重新请求前仍需显式同意 |
| Research | Profile、历史 Runs、Inbox 数据保留；本次 identity conflict 不应让整次 Run `failed`；错误原因有诊断记录 |
| Review / Publisher | Proposals、Imports、Review 列表可查看；若测试发布，使用可丢弃记录并确认生成 Git commit，无误改真实内容 |
| 安全访问 | 通过 Tailscale 正常；主机端口仍仅绑定 `127.0.0.1`，未直接公开 API/前端 |

如有 UI/数据/安全问题：**保持 Research Timer 停止，记录页面路径、操作、截图和后端日志后再处理**。服务可以短暂用于人工查看，但不要声称完整验收通过。

## 11. 备份恢复演练：只在隔离目录进行

**禁止直接将备份文件解压覆盖 `/srv/KnowledgeBase`，禁止覆盖运行中的 Runtime DB。** 以下演练只验证 Git bundle 可克隆、SQLite 可读取、Storage 可展开，不会替换生产服务：


## 12. 出现异常时的处置规则

| 阶段 | 发现异常 | 正确处理 |
|---|---|---|
| 备份前 / 备份中 | Git 脏、归档缺失、SQLite integrity 失败 | 停止升级；备份脚本会尝试重新启动旧服务；先解决备份问题 |
| Git Merge | Publisher 与上游冲突 | 不 reset/rebase；保持 Timer 停止，人工解决冲突，重做编译和检查 |
| Docker Build | 构建失败 | 不进行迁移；保留备份与日志，修好镜像再继续 |
| Backend 启动/迁移 | `unhealthy`、schema 不符、迁移异常 | 立即停止后续写操作；**不允许旧代码写入已迁移 DB**；制定单独恢复方案 |
| API / 业务核验 | 500、丢数据、渲染问题 | 保持 Research Timer 关闭；采集日志与问题路径，修复后重新按变更范围复验 |
| Research 首次 Tick | `failed` 或持续部分失败 | 暂停 Timer；读取 Run `error_summary` 和 systemd 日志，不重复创建付费手动任务 |
| 需要回退 | 已发生数据库迁移/业务写入 | 先停所有写入，针对**升级前快照**制定完整 Git+Runtime+Storage 恢复计划；不要只降级镜像或代码 |
