# KnowledgeBase 生产服务器版本更新与验收手册

> 适用：单用户 KnowledgeBase；Linux 主机，部署账号 `agent`，仓库 `/srv/KnowledgeBase`；Docker Compose 生产版；通过 Tailscale 等受控私网访问；Research 由主机 systemd Timer 触发。
>
> 目标：把已审查并通过 CI 的开发仓库 `main` 合并到**存在本地 Publisher 提交**的生产仓库，同时保全 Canonical Git 历史、Runtime SQLite 与 `storage/`。
>
> 本文是**日常版本升级流程**，不是清空测试 Term、删除正式知识或灾难恢复操作手册。这些具有不同数据风险的操作要单独执行、单独验收。涉及 root 的 `systemctl start/stop` 由 root 终端完成；`agent` 不必拥有 sudo 权限。

## 0. 放行条件与升级记录

开始前先确认：

- 目标是 GitHub `main` 中**确定的 40 位 SHA**，该 SHA 对应的 CI 已成功；已审查本次变更对 Runtime schema、Research Worker、Canonical 及前端交互的影响。
- 没有未解决的部署阻断问题。CI 通过只说明自动化检查通过，**不等于**生产环境的真实 AI/浏览器验收通过。
- 生产 Git remote 的可见性符合知识内容的隐私要求。Tailscale 仅保护应用访问，**不会保护已推送至公开仓库的笔记**。
- 选择维护时段并暂停业务写入；升级期间避免在网页中保存 Draft、发布知识或手工触发 Research。
- 日常生产升级**必须创建并验证备份**；只有另行明确授权的测试数据销毁任务可以采取不同策略，不能把“不备份测试 Term”理解为“不备份生产升级”。

每次记录（本手册不固化任何发布 SHA）：

```text
目标 main SHA（40 位）：
该 SHA 的 CI URL：
变更范围（Frontend / Backend / DB Migration / Research / Canonical）：
升级前生产 HEAD：
升级前 Research Timer：active / inactive
备份归档绝对路径与 SHA256：
升级前 Runtime schema：
升级后生产 HEAD：
升级后 Runtime schema：
```

**通过条件**：部署账号、`main`、干净工作区、旧服务/SQLite 正常，磁盘有足够容量。生产 `main` 领先 `origin/main` 若干提交是 Publisher 本地提交的正常表现，**不能据此重置**。如有未提交更改、数据库损坏或服务异常，先定位再升级。

记录 Timer 的**升级前状态**：`active` 或 `inactive`，用于决定后续是否恢复；Research Service 不在运行期间显示 `inactive` 属于正常。

## 2. root：停止自动 Research

若 Timer 已经 `inactive`，保持原状即可；若处于 `active`，由 root 终端执行：

```bash
systemctl stop knowledgebase-research.timer
systemctl is-active knowledgebase-research.timer || true
systemctl is-active knowledgebase-research.service || true
```

必须确认 **Timer 与正在执行的 Service 均不再运行**后再进入代码更新。停止 Timer 不会自动终止已经启动的 Research Service；若 Service 仍为 `active`，等待其自然完成。不要为了升级而强行中断运行中的 Research 写入。

## 3. agent：正式备份并验证归档

仓库现有脚本已实现 Research 锁协调、停服务、Git bundle + SQLite 在线备份 + Storage 归档，以及退出时尝试恢复旧服务：

```bash
cd /srv/KnowledgeBase
./scripts/production-backup.sh
```

预期看到 `Created /backups/knowledgebase-<UTC时间戳>.tar.gz (...)`；`/backups` 是**容器内路径**，主机目录由 `.env` 的 `KB_BACKUP_DIRECTORY` 映射，通常为 `/srv/KnowledgeBase-backups`。备份脚本结束后会**重新启动旧版 Backend/Frontend**，后续更新代码前须再次停止。

**必须手动指定本次输出对应的归档**，不要依赖“目录下最新一个文件”，以免误用旧备份或本次升级后生成的第二份备份：

```bash
cd /srv/KnowledgeBase

bash <<'BASH'
set -Eeuo pipefail
BACKUP_ARCHIVE='/srv/KnowledgeBase-backups/knowledgebase-请替换为本次实际文件名.tar.gz'
OLD_HEAD="$(git rev-parse HEAD)"
test -s "$BACKUP_ARCHIVE"
TMP="$(mktemp -d)"
trap 'rm -rf "$TMP"' EXIT

tar -tzf "$BACKUP_ARCHIVE" >/dev/null
tar -xzf "$BACKUP_ARCHIVE" -C "$TMP" \
  knowledge.bundle runtime/knowledge.db storage.tar.gz manifest.json

git bundle verify "$TMP/knowledge.bundle"
git bundle list-heads "$TMP/knowledge.bundle" | \
  awk -v old="$OLD_HEAD" '$1 == old {found=1} END {exit !found}'
tar -tzf "$TMP/storage.tar.gz" >/dev/null

python3 - "$TMP/runtime/knowledge.db" "$TMP/manifest.json" <<'PY'
import json, sqlite3, sys
from pathlib import Path
p, manifest = Path(sys.argv[1]).resolve(), Path(sys.argv[2])
meta = json.loads(manifest.read_text(encoding='utf-8'))
assert {'knowledge.bundle', 'runtime/knowledge.db', 'storage.tar.gz'} <= set(meta['contents'])
c = sqlite3.connect(p.as_uri() + '?mode=ro', uri=True)
print('Backup schema:', c.execute('PRAGMA user_version').fetchone()[0])
check = c.execute('PRAGMA integrity_check').fetchone()[0]
print('Backup integrity:', check)
assert check == 'ok'
c.close()
PY

sha256sum "$BACKUP_ARCHIVE"
echo 'BACKUP VERIFIED: PASS'
BASH
```

**验收**：归档可读取；包含升级前完整 HEAD 的 Git bundle；SQLite `integrity_check: ok`；Storage 可解压；记录备份的**准确绝对路径和 SHA256**。`.env` 不在归档中，凭证需通过独立的安全渠道保管；备份建议另存到第二个受保护位置。

## 4. agent：保留两边历史的 Git Merge + 串行构建

此步骤停止 Web、修改 Git 并构建镜像，但**不启动新版容器/数据库迁移**。在 2 核、内存有限的服务器上，**串行**构建 Backend 与 Frontend。

```bash
cd /srv/KnowledgeBase

bash <<'BASH'
set -Eeuo pipefail
COMPOSE=(docker compose --env-file .env -f docker-compose.production.yml)
TARGET_SHA='<填写已审查且 CI 成功的 main 完整 40 位 SHA>'

[[ "$TARGET_SHA" =~ ^[0-9a-f]{40}$ ]] || { echo 'ERROR: target SHA invalid'; exit 1; }
test "$(git branch --show-current)" = main
test -z "$(git status --porcelain --untracked-files=all)"
if systemctl is-active --quiet knowledgebase-research.timer || \
   systemctl is-active --quiet knowledgebase-research.service; then
  echo 'ERROR: Research is still active'; exit 1
fi

OLD_HEAD="$(git rev-parse HEAD)"
git fetch origin main
REMOTE_HEAD="$(git rev-parse refs/remotes/origin/main)"
test "$TARGET_SHA" = "$REMOTE_HEAD" || {
  echo 'ERROR: origin/main differs from reviewed CI SHA'; exit 1;
}

echo "Old production: $OLD_HEAD"
echo "Reviewed remote: $TARGET_SHA"
"${COMPOSE[@]}" stop frontend backend

if ! git merge-base --is-ancestor "$TARGET_SHA" HEAD; then
  git merge --no-edit "$TARGET_SHA"
fi

git merge-base --is-ancestor "$OLD_HEAD" HEAD
git merge-base --is-ancestor "$TARGET_SHA" HEAD
test -z "$(git status --porcelain --untracked-files=all)"
"${COMPOSE[@]}" config -q

echo '=== Build Backend ==='
"${COMPOSE[@]}" build backend

echo '=== Build Frontend ==='
"${COMPOSE[@]}" build frontend

# 检查新镜像标签；不要在旧容器仍引用已替换镜像时调用 docker compose images。
docker image inspect knowledgebase-backend:latest knowledgebase-frontend:latest >/dev/null

echo "Production HEAD: $(git rev-parse HEAD)"
echo "Preserved HEAD: $OLD_HEAD"
echo "Included target: $TARGET_SHA"
echo 'MERGE + BUILD: PASS (Runtime migration not started)'
BASH
```

**通过条件**：两个提交都是新 `HEAD` 的祖先、Git 工作区干净、Compose 配置与两次构建成功。新 HEAD 通常是一个 **Merge Commit**，不必等于远端提交。

**注意旧容器镜像问题**：旧容器可能仍指向已被替换的镜像 SHA，运行 `docker compose images` 会报 `No such image`；这并不能单独证明构建失败。检查新镜像标签或重新创建后的容器即可。若自定义了 `COMPOSE_PROJECT_NAME`，相应调整 `docker image inspect` 的镜像名。

如果 Merge 冲突或构建失败：**停止后续步骤**，保存日志，不执行 `reset --hard`、`rebase`、`down -v`、`docker system prune`，也不擅自回退数据库。若未启动新版 Backend，数据库通常仍保持旧 schema，但应以实际检查为准。

## 5. agent：只启动新版 Backend、迁移及知识校验

**启动新版 Backend 可能触发 SQLite schema migration**。该操作已经越过纯代码更新阶段，必须先确认本次升级前备份有效。

```bash
cd /srv/KnowledgeBase

bash <<'BASH'
set -Eeuo pipefail
COMPOSE=(docker compose --env-file .env -f docker-compose.production.yml)

"${COMPOSE[@]}" up -d --no-deps --no-build backend
CID="$("${COMPOSE[@]}" ps -q backend)"
test -n "$CID"

HEALTH='unknown'
for i in $(seq 1 40); do
  HEALTH="$(docker inspect -f '{{if .State.Health}}{{.State.Health.Status}}{{else}}no-healthcheck{{end}}' "$CID")"
  if [ "$HEALTH" = healthy ] || [ "$HEALTH" = unhealthy ]; then break; fi
  sleep 3
done
if [ "$HEALTH" != healthy ]; then
  "${COMPOSE[@]}" logs --tail=120 backend
  echo "ERROR: Backend health=$HEALTH"; exit 1
fi

echo '=== DB schema / integrity ==='
"${COMPOSE[@]}" exec -T backend python - <<'PY'
import sqlite3
from backend.app.db.migrations import CURRENT_SCHEMA_VERSION
c = sqlite3.connect('file:/workspace/runtime/knowledge.db?mode=ro', uri=True)
expected = CURRENT_SCHEMA_VERSION
actual = c.execute('PRAGMA user_version').fetchone()[0]
check = c.execute('PRAGMA integrity_check').fetchone()[0]
print('Expected schema:', expected)
print('Actual schema:', actual)
print('SQLite integrity:', check)
assert actual == expected
assert check == 'ok'
c.close()
PY

echo '=== Canonical / derived index / Research config ==='
"${COMPOSE[@]}" exec -T backend python /workspace/tools/kb.py check
"${COMPOSE[@]}" exec -T backend python /workspace/tools/kb.py rebuild
"${COMPOSE[@]}" exec -T backend python /workspace/tools/research.py check
"${COMPOSE[@]}" exec -T backend python /workspace/tools/research.py status

echo 'BACKEND / DB / CANONICAL / INDEX / RESEARCH: PASS'
BASH
```

`kb.py rebuild` 重建的是可再生索引，不是删除 Runtime 原始记录。**此处的 Research 命令只有 `check/status`，没有 `run/tick`，不会主动发起检索或 DeepSeek 调用。** 如果迁移失败，立即停止进一步写入；不要直接让旧 Backend 操作可能已经迁移的数据库。

## 6. agent：与升级前快照对比持久化数据

仅比较**升级前固定归档**与当前 Runtime。此检查只读，可发现误删表或异常减员；记录数相同仍不足以证明每条记录内容不变。

```bash
cd /srv/KnowledgeBase

python3 - <<'PY'
import sqlite3, tarfile, tempfile, shutil
from pathlib import Path

BACKUP_ARCHIVE = Path('/srv/KnowledgeBase-backups/knowledgebase-请替换为本次实际文件名.tar.gz')
assert BACKUP_ARCHIVE.is_file(), BACKUP_ARCHIVE

tables = (
    'drafts', 'proposals', 'import_jobs', 'import_items',
    'research_works', 'research_discoveries', 'research_candidates', 'research_runs',
    'research_profile_state', 'research_run_requests',
    'term_candidates', 'term_candidate_evidence', 'rejected_candidates',
    'term_entity_relations', 'term_discovery_runs', 'term_discovery_run_items',
    'document_term_analysis_state', 'corpus_analysis_state',
    'presentation_annotations', 'collection_progress', 'usage_events',
)

def counts(db):
    existing = {row[0] for row in db.execute("SELECT name FROM sqlite_master WHERE type='table'")}
    return {name: db.execute(f'SELECT COUNT(*) FROM "{name}"').fetchone()[0]
            for name in tables if name in existing}

with tempfile.TemporaryDirectory(prefix='kb-upgrade-audit-') as tmp:
    old_path = Path(tmp) / 'before.db'
    with tarfile.open(BACKUP_ARCHIVE, 'r:gz') as archive:
        member = archive.extractfile('runtime/knowledge.db')
        assert member is not None
        with member, old_path.open('wb') as dest:
            shutil.copyfileobj(member, dest)
    old = sqlite3.connect(old_path.resolve().as_uri() + '?mode=ro', uri=True)
    new = sqlite3.connect(Path('runtime/knowledge.db').resolve().as_uri() + '?mode=ro', uri=True)
    try:
        before, after = counts(old), counts(new)
        print('Compare against:', BACKUP_ARCHIVE)
        decreased = []
        for name, previous in before.items():
            assert name in after, f'Missing table: {name}'
            current = after[name]
            print(f'{name}: {previous} -> {current}')
            if current < previous:
                decreased.append((name, previous, current))
        if decreased:
            raise AssertionError(f'Unexpected decreases; review migration/approved deletions: {decreased}')
        print('PERSISTENT COUNTS: PASS')
    finally:
        old.close()
        new.close()
PY
```

如果本次**特意执行过**已审核的数据清理或迁移转换，行数下降不必然代表事故，但不可直接跳过：需逐项核对变更说明和影响范围后记录“有解释的差异”。一般版本升级不应附带清空候选、历史或正式内容。

## 7. agent：启动 Frontend、健康检查和 API Smoke

生产 Frontend 镜像**已包含 Docker HEALTHCHECK**（见 `frontend/Dockerfile.production`）；因此新容器应检查 `healthy`，不再仅凭 `Running` 判定。生产 Compose 默认只在 `127.0.0.1:8080` 提供 Web 服务；如果实际 `.env` 改过 `KB_HTTP_PORT`，下方 `BASE_URL` 也要同步调整。

```bash
cd /srv/KnowledgeBase

bash <<'BASH'
set -Eeuo pipefail
COMPOSE=(docker compose --env-file .env -f docker-compose.production.yml)
BASE_URL='http://127.0.0.1:8080'  # 非默认端口/绑定地址时改为当前本机可访问地址

"${COMPOSE[@]}" up -d --no-deps --no-build frontend
CID="$("${COMPOSE[@]}" ps -q frontend)"
test -n "$CID"

HEALTH='unknown'
for i in $(seq 1 40); do
  HEALTH="$(docker inspect -f '{{if .State.Health}}{{.State.Health.Status}}{{else}}no-healthcheck{{end}}' "$CID")"
  if [ "$HEALTH" = healthy ] || [ "$HEALTH" = unhealthy ]; then break; fi
  sleep 3
done
if [ "$HEALTH" != healthy ]; then
  "${COMPOSE[@]}" logs --tail=120 frontend
  echo "ERROR: Frontend health=$HEALTH"; exit 1
fi

BASE_URL="$BASE_URL" python3 - <<'PY'
import json, os, urllib.request
base = os.environ['BASE_URL'].rstrip('/')
paths = (
    '/api/ui/summary', '/api/library/document-states',
    '/api/library/source-states', '/api/documents', '/api/terms',
    '/api/terms/candidates', '/api/terms/discovery', '/api/sources',
    '/api/research/profiles', '/api/proposals',
    '/api/proposals?limit=1&target_type=term', '/api/imports',
    '/api/review/link-issues', '/api/annotations/stale', '/openapi.json',
)
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
for path in paths:
    with opener.open(base + path, timeout=30) as response:
        assert response.status == 200, path
        json.loads(response.read())
    print('PASS', path)
with opener.open(base + '/', timeout=30) as response:
    assert response.status == 200
    assert b'<html' in response.read().lower()
print('PASS /')
print('API SMOKE: PASS')
PY

"${COMPOSE[@]}" ps
echo 'WEB: PASS'
BASH
```

**通过条件**：Backend、Frontend 均 `healthy`，首页及重要只读 API 均 200，API 内容可解析为 JSON。若本次修改了路由，应附加相应接口；当前列表是基础 Smoke，不替代业务验收。

## 9. 浏览器与业务验收（按本次变更选择专项）

通过私有网络在真实浏览器中操作。**先验证读取，再验证必要的 Draft 写入**；不要随意消耗 DeepSeek 配额、运行付费 Research，或在正式知识中制造测试记录。

| 模块 | 基本验收点 |
|---|---|
| Home | 导航、摘要、推荐理由 Markdown/公式、展开收起、刷新状态 |
| Library / Import | 列表、Collections、Document/Source 打开；必要时验证导入候选创建 Draft |
| Reader / Workspace | 代码块、Mermaid、数学公式、高亮；Draft 保存、刷新、冲突保护 |
| Terms | Candidate 来源、接受/拒绝行为、Term Draft、深度 `standard` 默认值及持久化、双语内容与 Proposal 人工采用 |
| Research | Profile、历史 Runs、候选及状态保留；`partial/failed` 诊断可见 |
| Publisher | 如本次涉及发布：先用可丢弃草稿预检，发布后确认 Canonical Git 提交、索引和原有知识无误 |
| 安全 | 浏览器经 Tailscale/受控私网访问；Backend 8000 未直通公网，Web 监听地址符合访问控制策略 |

每次额外列出与本次提交直接对应的专项交互。**不要把未来尚未开发的 Term 页面重设计、双语重写等需求当成当前代码已完成的验收标准**；对尚未上线的功能另记待办。

如果要真实调用 DeepSeek：使用明确同意的少量测试请求，检查生成内容质量以及“AI Proposal → 人工采用到 Draft → 单独发布”的隔离，且不得因测试反复调用；已存在匹配 Proposal 时优先复用。

若出现数据丢失、500、错误写入或明显渲染故障：Research Timer 继续关闭，保存页面路径、操作步骤、浏览器截图及服务日志后再处理。

## 10. Research Timer：按原状态及明确授权决定是否启用

**不执行默认的无条件 `systemctl start`。** 如果升级前 Timer 就是 `inactive`，或本次 Research 尚未验收/不希望自动检索，则继续保持 `inactive`。只有确认业务验收完成且**明确决定启用定时检索**时，root 才执行：

```bash
systemctl start knowledgebase-research.timer
systemctl is-active knowledgebase-research.timer
systemctl list-timers knowledgebase-research.timer --all
systemctl status knowledgebase-research.timer --no-pager
```

仓库当前 `deploy/systemd/knowledgebase-research.timer` 使用 `OnActiveSec=2min`、`OnUnitInactiveSec=2min`，**恢复后可能很快触发真实 Research Tick**，其后续模型调用可能产生费用。因此不要把它当作纯粹的健康检查。

`agent` 可只读检查：

```bash
cd /srv/KnowledgeBase
docker compose --env-file .env -f docker-compose.production.yml exec -T backend \
  python /workspace/tools/research.py status
```

若经授权恢复 Timer，等待自然触发后由 root 查阅：

```bash
journalctl -u knowledgebase-research.service -n 100 --no-pager
```

若状态持续 `failed`，或有与本次变更相关的异常，关闭 Timer 并分析 Run 日志；不要立即多次手动执行 `run --manual`。Service 在没有运行时显示 `inactive` 是正常的。

## 11. 隔离环境恢复演练（可选，但建议定期执行）

**绝对不要直接将归档解压覆盖正在运行的 `/srv/KnowledgeBase`。** 此步骤只验证备份可独立展开/读取，不启动新服务，也不改生产数据。

```bash
cd /srv/KnowledgeBase

bash <<'BASH'
set -Eeuo pipefail
BACKUP_ARCHIVE='/srv/KnowledgeBase-backups/knowledgebase-请替换为已验证文件名.tar.gz'
test -s "$BACKUP_ARCHIVE"
TMP="$(mktemp -d)"
trap 'rm -rf "$TMP"' EXIT
mkdir -p "$TMP/unpack"
tar -xzf "$BACKUP_ARCHIVE" -C "$TMP/unpack"
git clone -q "$TMP/unpack/knowledge.bundle" "$TMP/restore-checkout"
mkdir -p "$TMP/restore-checkout/runtime"
cp "$TMP/unpack/runtime/knowledge.db" "$TMP/restore-checkout/runtime/knowledge.db"
tar -xzf "$TMP/unpack/storage.tar.gz" -C "$TMP/restore-checkout"
python3 - "$TMP/restore-checkout/runtime/knowledge.db" <<'PY'

```

## 12. 异常处置与禁止动作

| 阶段 | 表现 | 处理 |
|---|---|---|
| 备份 | 工作区脏、归档验证失败、SQLite 损坏 | 暂停更新；先排除，不以存在旧归档替代本次备份 |
| Git Merge | 冲突或本地 Publisher 提交风险 | 保留现场，人工逐文件解决；不能重置/变基覆盖 Canonical |
| Docker Build | `apt`/`npm` 下载失败、OOM 或构建失败 | 暂停启动新版；记录日志，确认资源和镜像仓库后重试构建 |
| 旧容器镜像 | `docker compose images` 提示 `No such image: sha256:...` | 先检查 `docker image inspect` 新镜像及新容器；旧容器引用已替换镜像并非数据库损坏 |
| Backend / DB | `unhealthy`、schema 不符、迁移失败 | 停止进一步写入；不可只回退代码而继续使用可能已升级的 DB |
| 数据对比 | 持久化表消失或记录数减少 | 对照迁移和是否有批准的清理；未获解释不得放行 |
| API / 浏览器 | 5xx、重要交互错误 | Research Timer 保持关闭，采集日志后修复、按范围复测 |
| Research | Tick 失败或严重异常 | 停止 Timer，分析 Run 与 systemd 日志，避免反复付费试错 |

**禁止作为“快速修复”执行**：`git reset --hard`、在生产历史上 `rebase`、`docker compose down -v`、`docker system prune`、直接清理整个 Runtime/Storage、只回退镜像而不核对数据库 schema、直接覆盖正在运行的 SQLite。单独授权的测试数据删除是独立任务，必须精确界定对象和不受影响的数据。
